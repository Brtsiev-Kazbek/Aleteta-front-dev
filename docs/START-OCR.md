# Запустить распознавание: по шагам

Распознавание делает не приложение, а **исполнитель** — программа на стороне
Supabase (Edge Function `ai-worker`). Приложение только кладёт задание в
очередь; читает страницы и звонит модели исполнитель.

Отсюда и разделение, из-за которого путается большинство: **у приложения и у
исполнителя разные переменные окружения**. Приложение читает `.env.local` (при
локальном запуске) или переменные своего хостинга; исполнитель живёт в
Supabase и о них не знает вовсе.

Если файл висит в «В очереди» и на routerai нет запросов — значит, исполнителя
нет. Это нормальное состояние до того, как выполнены шаги ниже.

А если файл сразу помечен «не удалось» — исполнитель есть и работает, причина
написана прямо на странице. Чаще всего это ключ.

---

## Куда идёт ключ к модели

Коротко, потому что путают чаще всего остального.

| Что | Куда | Почему |
|---|---|---|
| `LLM_API_KEY` | **Только в секреты исполнителя** (Supabase) | Приложение не должно уметь позвать модель напрямую даже теоретически |
| `LLM_BASE_URL`, `LLM_MODEL_VISION` | В оба места: переменные приложения и секреты исполнителя | Приложению — чтобы знать, какую модель просить; исполнителю — чтобы её позвать |
| `SUPABASE_SERVICE_ROLE_KEY` | Нигде не обязателен | И приложение, и расписание будят исполнителя публичным ключом |

В репозиторий не попадает ничего из этого.

---

## Что уже сделано и чего не хватает

Расписание, очередь и права настроены миграциями — трогать их не нужно.
Исполнитель будится сам: приложение стучится к нему сразу после постановки
задания, а раз в минуту его дёргает расписание. Служебный ключ для этого не
требуется — исполнителю ключ звонящего не нужен вовсе, к базе он ходит своим.

Остаются два шага, и оба делаются в браузере.

---

## Шаг 1. Ключ к модели

Ключ заводится у маршрутизатора **с потолком расхода**. Мастер-ключ для этого
не годится: он управляет ключами, а обращаться к моделям им нельзя.

```bash
curl https://routerai.ru/api/v1/keys --request POST ^
  --header "Authorization: Bearer <мастер-ключ>" ^
  --header "Content-Type: application/json" ^
  --data "{\"name\":\"aleteya-ocr\",\"limit\":1000}"
```

Проверьте, что ключ рабочий, не отходя от кассы. Положите его в `.env.local`
строкой `LLM_API_KEY=...` и запустите:

```bash
npm run check:vision -- --whoami
npm run check:vision -- скан.pdf --model qwen/qwen3-vl-32b-instruct --page 3
```

Вторая команда проходит ровно тот путь, которым пойдёт исполнитель: тот же
движок, тот же кодировщик, тот же запрос. Картинка сохранится рядом с PDF —
видно, что именно ушло в модель.

**Если эта команда сработала, а через сайт не работает — дело не в ключе и не в
модели.** Идите дальше.

---

## Шаг 2. Переменные приложения

При локальном запуске — файл `.env.local` в корне проекта. На хостинге — его
панель переменных окружения. Три штуки:

| Переменная | Значение |
|---|---|
| `LLM_BASE_URL` | `https://routerai.ru/api/v1` |
| `LLM_MODEL_VISION` | `qwen/qwen3-vl-32b-instruct` |

Обе нужны, чтобы приложение знало, какую модель просить, и вообще согласилось
поставить задание. Больше ничего не требуется: `SUPABASE_SERVICE_ROLE_KEY`
необязателен — см. раздел ниже.

**Ключ `LLM_API_KEY` сюда не кладите.** Приложение не должно уметь позвать
модель напрямую даже теоретически.

После правки переменных приложение надо перезапустить: локально — остановить
`npm run dev` и запустить снова (на лету `.env.local` не перечитывается), на
хостинге — пересобрать сайт.

---

## Шаг 3. Выложить исполнителя

Один раз, с машины разработчика. Устанавливать ничего не нужно — `npx`
скачает CLI сам:

```bash
npx supabase login
npx supabase functions deploy ai-worker --project-ref <ref проекта>
```

`login` откроет браузер. `--project-ref` избавляет от `link` и от вопроса про
пароль базы. Ref виден в адресе проекта: `https://<ref>.supabase.co`.

Проверить: Supabase → Edge Functions. В списке должна быть `ai-worker` со
статусом ACTIVE.

Это единственный шаг, требующий командной строки, и делается он один раз —
пока не изменится код исполнителя.

---

## Шаг 4. Секреты исполнителя — в браузере

Supabase → Project Settings → **Edge Functions** → Secrets → Add new secret.
Четыре штуки:

| Имя | Значение |
|---|---|
| `LLM_API_KEY` | обычный ключ API маршрутизатора |
| `LLM_BASE_URL` | `https://routerai.ru/api/v1` |
| `LLM_MODEL_VISION` | `qwen/qwen3-vl-32b-instruct` |
| `LLM_MODE` | `live` |

**`LLM_MODE=live` обязателен.** По умолчанию стоит `replay`: ответы берутся из
журнала по отпечатку входа, и обращений к модели не происходит вовсе. Это
режим разработки, в нём распознавание вернёт пустоту.

**Мастер-ключ не подойдёт.** Он управляет ключами и лимитами, но обращаться к
моделям им нельзя — маршрутизатор отвечает 401. Если ошиблись, на странице
распознавания это будет написано прямо: «Маршрутизатор не принял ключ».

Секреты применяются сразу, перевыкладывать функцию не нужно. Нажмите
«Распознать заново» — задание пойдёт с новым ключом.

Кто предпочитает командную строку:

```bash
npx supabase secrets set --project-ref <ref> LLM_API_KEY=... LLM_BASE_URL=https://routerai.ru/api/v1 LLM_MODEL_VISION=qwen/qwen3-vl-32b-instruct LLM_MODE=live
```

---

## Необязательное: служебный ключ

Ничего из этого делать не нужно — всё работает и без него. Здесь лишь описано,
что даёт `SUPABASE_SERVICE_ROLE_KEY`, если вы его всё-таки зададите.

И приложение, и расписание будят исполнителя публичным ключом проекта. Это
законно: исполнитель ключом звонящего не пользуется — к базе он ходит своим,
который Supabase подставляет ему в окружение. От звонящего требуется одно —
пройти проверку JWT на входе, а публичный ключ её проходит.

Служебный ключ, положенный в переменные приложения или в `vault`, берётся
первым. Разница не в правах, а в том, что публичный ключ общий для всего
проекта, и однажды его смена не должна тихо ломать расписание.

---

## Проверка

Загрузите скан на странице «Распознавание». Строка файла должна за несколько
секунд перейти из «В очереди» в «Страница 1 из N».

Если не переходит, смотрите по порядку — каждый запрос отвечает на свой вопрос.

**Задание вообще создалось?**

```sql
select id, task, status, attempts, error, created_at
from public.ai_jobs order by created_at desc limit 5;
```

Пусто — приложение не смогло поставить задание. Это шаг 2: нет `LLM_BASE_URL`
или `LLM_MODEL_VISION`, либо приложение не перезапускали после их добавления.
В журнале приложения это видно строкой `job.enqueue.not-configured`.

**До исполнителя достучались?**

```sql
select id, status_code, created from net._http_response
order by created desc limit 5;
```

Пусто — до функции не достучались. Код 404 — функции нет: шаг 3.

**Что лежит в секретах исполнителя?**

Прочитать их снаружи нельзя ни из панели, ни запросом — поэтому есть отдельная
маленькая функция, которая отвечает за них сама. Очередь она не трогает и денег
не тратит: спрашивает служебный адрес маршрутизатора, а не модель.

```bash
npx supabase functions deploy check-key --project-ref <ref>
```

Позвать её можно из SQL-редактора Supabase:

```sql
select net.http_post(
  url := 'https://<ref>.supabase.co/functions/v1/check-key',
  headers := jsonb_build_object(
    'authorization', 'Bearer <публичный ключ проекта>'
  ),
  body := '{}'::jsonb
) as номер;

-- через пару секунд, подставив номер из ответа:
select status_code, content from net._http_response where id = <номер>;
```

Ответ выглядит так:

```json
{
  "ключ": { "задан": true, "длина": 35, "начинается_на_sk": true,
            "были_лишние_знаки": false },
  "адрес": "https://routerai.ru/api/v1",
  "вывод": "ключ не принят: неверный, отозванный или мастер-ключ"
}
```

Сам ключ наружу не выходит. Но по длине и по «были лишние знаки» сразу видно,
пусто там, обрезано или прилип пробел, — а «вывод» отвечает на главный вопрос
без гаданий.

**Что говорит сам исполнитель?**

Причина отказа видна прямо на странице «Распознавание»: у упавшего файла она
написана дословно — «Маршрутизатор не принял ключ», «Не удалось получить файл»
и так далее. То же самое в базе:

```sql
select status, attempts, error from public.ai_jobs
order by created_at desc limit 5;
```

Подробности выполнения — в Supabase → Edge Functions → ai-worker → Logs, либо
командой `npx supabase functions logs ai-worker --project-ref <ref>`.

**Расписание живо?**

```sql
select jobname, schedule, active from cron.job;
select status, start_time from cron.job_run_details
order by start_time desc limit 5;
```

## Журнал

Приложение пишет в консоль события, а не предложения:

```
14:22:07.412 INFO  upload.storage файл=скан.pdf байт=2411096 мс=1840
14:22:07.998 INFO  document.register документ=b56390d3 дело=«без дела»
14:22:08.115 INFO  job.enqueue задача=ocr задание=7f21ac04 источник=новое мс=210
14:22:08.140 WARN  job.poke.skip причина=«нет SUPABASE_SERVICE_ROLE_KEY»
14:22:10.201 INFO  ocr.watch.start документ=b56390d3 наблюдателей=1
```

По имени события можно грепать: `job.` — очередь, `ocr.watch` — опрос
состояния, `upload.` — загрузка файла. Ключи и токены не печатаются никогда:
поля с такими именами скрываются по образцу.

Подробность задаётся `LOG_LEVEL` (сервер) и `NEXT_PUBLIC_LOG_LEVEL` (браузер):
`debug`, `info`, `warn`, `error`. В разработке по умолчанию `debug`, на боевом
— `info`, потому что отладочные события идут на каждый тик опроса.

Что искать при разборе:

| Строка | Значит |
|---|---|
| `job.enqueue.not-configured` | Нет модели для этой задачи — шаг 2 |
| `job.poke.skip` | Нет служебного ключа: исполнитель проснётся по расписанию |
| `job.poke.not-deployed` | Исполнителя нет — шаг 3 |
| `ocr.watch.error` | Сервер не отвечает на опрос; после трёх подряд опрос прекращается |
| `ocr.watch.settled` | Файл дочитан, наблюдатель остановлен |

---

## Что сколько стоит

Страница скана — около **0,076 ₽** при qwen3-vl-32b: примерно 1600 токенов на
вход и 1300 на выход, из которых три четверти цены приходится на выход.

Страница с текстовым слоем — **бесплатно**: текст берётся прямо из файла, модель
не вызывается. В расшифровке такие страницы помечены «Из файла».

Сто страниц скана — около 7,6 ₽ и примерно десять минут: страницы уходят в
модель волнами по десять.
