# Запустить распознавание: по шагам

Распознавание делает не приложение, а **исполнитель** — программа на стороне
Supabase (Edge Function `ai-worker`). Приложение только кладёт задание в
очередь; читает страницы и звонит модели исполнитель.

Отсюда и разделение, из-за которого путается большинство: **у приложения и у
исполнителя разные переменные окружения**. Приложение живёт в Netlify,
исполнитель — в Supabase, и переменных друг друга они не видят.

Если файл висит в «В очереди» и на routerai нет запросов — значит, исполнителя
нет. Это нормальное состояние до того, как выполнены шаги ниже.

Нужен Node (он у вас есть) и десять минут.

---

## Куда идёт ключ к модели

Коротко, потому что путают чаще всего остального.

| Что | Куда | Почему |
|---|---|---|
| `LLM_API_KEY` | **Только в секреты исполнителя** (Supabase) | Приложение не должно уметь позвать модель напрямую даже теоретически |
| `LLM_BASE_URL`, `LLM_MODEL_VISION` | В оба места: Netlify и секреты исполнителя | Приложению — чтобы знать, какую модель просить; исполнителю — чтобы её позвать |
| `SUPABASE_SERVICE_ROLE_KEY` | Netlify и `vault` в базе | Приложению — толкнуть исполнителя; расписанию — разбудить его |

В репозиторий не попадает ничего из этого. Файл `supabase/functions/.env`,
куда ключ кладут на своей машине, закрыт правилом в `.gitignore`.

---

## Быстрый путь: один батник

Всё, что нельзя сделать из браузера, делает скрипт. Из папки проекта:

```
scripts\setup-ocr.bat
```

или `npm run setup:ocr`. Он спросит два ключа — к модели и служебный
Supabase, — а дальше сам: войдёт в Supabase, выложит исполнителя, задаст ему
секреты, положит служебный ключ в `vault` для расписания и проверит, что
исполнитель отвечает.

Ключи вводятся вслепую и на диск не пишутся: секреты уходят через временный
файл, который удаляется сразу после.

Одного он сделать не может — переменных Netlify: у панели свой вход, и
подставлять туда чужие ключи скрипт не вправе. В конце он напомнит, что и куда
вписать.

Дальше — то же самое руками, по шагам, с проверкой на каждом.

## Шаг 1. Ключ к модели

Ключ заводится у маршрутизатора **с потолком расхода**. Мастер-ключ для этого
не годится: он управляет ключами, а обращаться к моделям им нельзя.

```bash
curl https://routerai.ru/api/v1/keys --request POST ^
  --header "Authorization: Bearer <мастер-ключ>" ^
  --header "Content-Type: application/json" ^
  --data "{\"name\":\"aleteya-ocr\",\"limit\":1000}"
```

Проверьте, что ключ рабочий, не отходя от кассы. Положите его в `.env.local`
строкой `LLM_API_KEY=...` и запустите:

```bash
npm run check:vision -- --whoami
npm run check:vision -- скан.pdf --model qwen/qwen3-vl-32b-instruct --page 3
```

Вторая команда проходит ровно тот путь, которым пойдёт исполнитель: тот же
движок, тот же кодировщик, тот же запрос. Картинка сохранится рядом с PDF —
видно, что именно ушло в модель.

**Если эта команда сработала, а через сайт не работает — дело не в ключе и не в
модели.** Идите дальше.

---

## Шаг 2. Переменные приложения (Netlify)

Site configuration → Environment variables. Три штуки:

| Переменная | Значение |
|---|---|
| `LLM_BASE_URL` | `https://routerai.ru/api/v1` |
| `LLM_MODEL_VISION` | `qwen/qwen3-vl-32b-instruct` |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API → `service_role` |

Первые две нужны, чтобы приложение знало, какую модель просить, и вообще
согласилось поставить задание. Третья — чтобы приложение могло толкнуть
исполнителя сразу после постановки, а не ждать минуту.

**Ключ `LLM_API_KEY` сюда не кладите.** Приложение не должно уметь позвать
модель напрямую даже теоретически.

После правки переменных Netlify надо пересобрать сайт: Deploys → Trigger
deploy → Clear cache and deploy site.

---

## Шаг 3. Выложить исполнителя

С вашей машины, из папки проекта. Устанавливать ничего не нужно — `npx`
скачает CLI сам.

```bash
npx supabase login
npx supabase link --project-ref mqbqpougnlewytqcgtoq
npm run worker:deploy
```

`login` откроет браузер и попросит подтвердить вход. `link` спросит пароль
базы — тот, что задавали при создании проекта; если забыли, его можно сменить
в Settings → Database → Reset database password.

Проверить, что получилось:

```bash
npx supabase functions list
```

В списке должна появиться `ai-worker`.

---

## Шаг 4. Секреты исполнителя

Это отдельный от Netlify набор — тот, который видит функция.

```bash
copy supabase\functions\.env.example supabase\functions\.env
```

Откройте `supabase/functions/.env`, впишите `LLM_API_KEY` и проверьте
`LLM_MODEL_VISION`. Затем:

```bash
npm run worker:secrets
```

**`LLM_MODE=live` обязателен.** По умолчанию стоит `replay`: ответы берутся из
журнала по отпечатку входа, и обращений к модели не происходит вовсе. Это режим
разработки, в нём распознавание при первом запуске вернёт пустоту.

Файл `.env` в этой папке в git не попадает — правило в `.gitignore` есть.

---

## Шаг 5. Ключ для расписания

Расписание уже создано миграцией и работает раз в минуту: возвращает зависшие
задания в очередь и будит исполнителя. Не хватает одного — служебного ключа,
которым оно к исполнителю обращается.

В SQL-редакторе Supabase, один раз:

```sql
select vault.create_secret('<служебный ключ>', 'service_role_key');
```

Ключ тот же, что в шаге 2 (`service_role`). В теле функции он лежал бы открытым
текстом — в дампе базы, в истории репозитория, — поэтому хранится в `vault`.

Пока ключа нет, расписание проходит вхолостую: молча, без ошибок в журнале.

## Проверка

Загрузите скан на странице «Распознавание». Строка файла должна за несколько
секунд перейти из «В очереди» в «Страница 1 из N».

Если не переходит, смотрите по порядку — каждый запрос отвечает на свой вопрос.

**Задание вообще создалось?**

```sql
select id, task, status, attempts, error, created_at
from public.ai_jobs order by created_at desc limit 5;
```

Пусто — приложение не смогло поставить задание. Это шаг 2: нет `LLM_BASE_URL`
или `LLM_MODEL_VISION`, либо Netlify не пересобрался после их добавления.

**До исполнителя достучались?**

```sql
select id, status_code, created from net._http_response
order by created desc limit 5;
```

Пусто — расписание не зовёт функцию: это шаг 5. Код 404 — функции нет: шаг 3.
Код 401 — ключ в `vault` неверный.

**Что говорит сам исполнитель?**

```bash
npm run worker:logs
```

Здесь будут отказы маршрутизатора и нехватка секретов — это шаг 4.

**Расписание живо?**

```sql
select jobname, schedule, active from cron.job;
select status, start_time from cron.job_run_details
order by start_time desc limit 5;
```

## Что сколько стоит

Страница скана — около **0,076 ₽** при qwen3-vl-32b: примерно 1600 токенов на
вход и 1300 на выход, из которых три четверти цены приходится на выход.

Страница с текстовым слоем — **бесплатно**: текст берётся прямо из файла, модель
не вызывается. В расшифровке такие страницы помечены «Из файла».

Сто страниц скана — около 7,6 ₽ и примерно десять минут: страницы уходят в
модель волнами по десять.
