# Бэкенд на Supabase

Как поднять базу, применить схему и подключить приложение. Docker не нужен:
работаем сразу с облачным проектом.

---

## 1. Проект в облаке

1. Заведите проект на supabase.com. Регион — **Frankfurt (eu-central-1)**:
   ближайший к РФ по задержке.
2. Пароль базы сохраните — он понадобится при первом `db push` и больше нигде.
3. Скопируйте `.env.example` в `.env.local` и заполните:

| Переменная | Где взять |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project Settings → API → Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | там же, `anon public` |
| `SUPABASE_SERVICE_ROLE_KEY` | там же, `service_role` — **только на сервере** |

Публичность первых двух — не упущение: доступ к данным ограничивают политики
в базе, а не секретность ключа. Третий обходит все политики, поэтому у него
нет префикса `NEXT_PUBLIC_` и он не должен попадать в браузер.

---

## 2. Применить схему

```bash
npx supabase login
npm run db:link -- <project-ref>
npm run db:push
```

`project-ref` — часть адреса проекта: `https://<project-ref>.supabase.co`.

Демонстрационные данные (те же три дела, что были в моках) заливаются отдельно:

```bash
npm run db:seed
```

После этого перегенерируйте типы — дальше файл ведёт генератор, руками его
не правят:

```bash
npm run db:types
```

**Схема меняется только миграциями.** Правка через веб-панель не попадёт в
репозиторий, и при переезде на self-hosted её никто не воспроизведёт. Новое
изменение — новый файл в `supabase/migrations`.

## 3. Что уже есть в базе

### Люди и доступ

| Таблица | Назначение |
|---|---|
| `profiles` | Публичные данные пользователя; `auth.users` наружу не отдаётся |
| `workspaces` | Арендатор: все данные принадлежат пространству, а не человеку |
| `workspace_members` | Роль в пространстве: `owner`, `admin`, `member`, `viewer` |
| `workspace_invites` | Приглашения по почте, принимаются автоматически при регистрации |

Роль `platform_role` в профиле — уровень всей установки, `user` или `admin`.
Администратор видит админ-панель и сводную статистику.

Регистрация обрабатывается триггером: на нового пользователя заводится
профиль и личное пространство, где он владелец, а незакрытые приглашения на
его адрес принимаются сразу.

### Продукт

| Таблица | Назначение |
|---|---|
| `entity_types` | Типы объектов. `workspace_id IS NULL` — встроенный, доступен всем |
| `cases` | Дела |
| `entities` | Объекты дела; реквизиты в `jsonb` |
| `documents` | Файлы: бакет и путь, **не URL** |
| `chat_messages` | Переписка с ассистентом, вместе с находками и ссылками на источники |
| `activity` | Лента действий по делу |

### Модель

| Таблица | Назначение |
|---|---|
| `ai_jobs` | Журнал всех AI-операций: очередь, вход, выход, токены, стоимость, правка человека |
| `document_reviews`, `review_findings` | Разбор договора по пунктам |
| `court_practice`, `finding_practice` | Судебная практика; поле `source` разводит демо и лицензированного поставщика |
| `document_chunks` | Фрагменты документов с векторами и полнотекстовым индексом |

### Статистика

| Что | Кому |
|---|---|
| `workspace_stats` | Участникам — показатели своего пространства |
| `ai_usage_daily` | Участникам — расход по дням, задачам и моделям |
| `platform_overview()` | Только администратору установки |
| `platform_workspaces()` | Только администратору: список пространств с владельцами |
| `platform_signups(days)` | Только администратору: регистрации по дням |

### Хранилище

| Бакет | Доступ |
|---|---|
| `case-documents` | Закрытый. Путь: `<workspace_id>/<case_id>/<файл>` — право выводится из членства |
| `avatars` | Публичный на чтение, запись только в свою папку |

## 3.1. Регистрация и формы

Экраны входа разведены по адресам: `/auth/login`, `/auth/register`,
`/auth/forgot-password`, `/auth/reset-password`. Все они работают через
серверные действия в `app/actions/auth.ts`, а не из браузера напрямую — cookie
сессии ставится заголовком ответа, иначе серверные компоненты на той же
навигации отрисовались бы ещё гостю.

Ссылка из письма приходит в `/auth/callback`. Обрабатываются оба вида —
`?code=` (поток PKCE) и `?token_hash=&type=`: какой пришлёт проект, зависит от
шаблонов писем, а не от кода приложения.

Форма регистрации спрашивает имя, должность и организацию. Все три уезжают в
метаданные пользователя, откуда их забирает триггер `app.handle_new_user`:
имя и должность — в профиль, организация — в название пространства.

**Приглашения.** Приглашение — строка в `workspace_invites`, письмо лишь
уведомление. Новому пользователю членство выдаёт триггер регистрации, уже
зарегистрированному — функция `public.accept_pending_invites()`, которая
вызывается при каждом входе. Сам себе членство пользователь вписать не может:
политика на `workspace_members` требует роль владельца или админа, а функция
сверяет почту приглашения с почтой вошедшего.

**Загрузка документов.** Файл идёт в хранилище прямо из браузера, минуя
серверное действие: предел на тело действия — мегабайты, а скан договора весит
десятки. Порядок такой: `prepareDocumentUploadAction` выдаёт путь (первый
сегмент — идентификатор пространства, по нему хранилище и решает, кому файл
доступен), браузер загружает содержимое, `registerDocumentAction` заводит
строку и сверяет, что путь относится к тому самому делу.

**Отзывчивость против согласованности.** Правки в таблице реквизитов
применяются к интерфейсу сразу, запись идёт следом (`sync()` в
`store/useAppStore.ts`). Отказ базы откатывает изменение и показывается
плашкой внизу экрана — иначе значение молча возвращалось бы к прежнему.

## 4. Что перенесено с клиента на сервер

**Валидация реквизитов.** Раньше проверки ИНН, КПП, СНИЛС и кадастрового
номера жили только в браузере — то есть их можно было обойти запросом мимо
интерфейса. Теперь это функция `app.validate_entity`, и триггер пересчитывает
`validation_errors` при каждой записи. Клиент физически не может объявить
объект валидным.

**Принадлежность пространству.** `workspace_id` у объектов, документов и
сообщений проставляется триггером из дела, а не принимается от клиента. Иначе
запись можно было бы приписать к чужому пространству, подставив его
идентификатор.

**Поиск по делу.** `search_case_chunks()` — гибридный: векторный плюс
полнотекстовый, объединение по взаимному рангу. По отдельности каждый способ
проваливает половину запросов: смысловой не находит точный кадастровый номер,
текстовый — перефразированное. Фильтр по делу зашит внутрь функции.

## 5. Чего в базе нет и не будет

Supabase — это хранение, доступ и оркестрация. Ни одну из AI-частей он не
делает сам:

| Нужно | Чем закрывать |
|---|---|
| Распознавание сканов | Внешний OCR либо vision-модель |
| Извлечение реквизитов, разбор договора, ассистент | Языковая модель через маршрутизатор |
| Судебная практика | Лицензированный источник; пока `source = 'demo'` |
| Сборка DOCX | Отдельный код; в Edge Functions тяжёлые библиотеки не поместятся |

## 6. Переезд на self-hosted

Заложено с самого начала, отдельной подготовки не потребует:

1. **Схема в миграциях** — воспроизводится одной командой на любом Postgres.
2. **В базе пути к файлам, не URL** — ссылка собирается на клиенте, поэтому
   смена адреса проекта ничего не ломает.
3. **Адреса и ключи в переменных окружения** — в коде их нет.
4. **`app.current_user_id()`** — единственное место, знающее про формат
   токена. Смена механизма аутентификации правит одну функцию, а не сотню
   политик.
5. **Бакеты заводятся миграцией**, а не кнопкой в панели — иначе на новом
   сервере их просто не будет.

Отдельно: собственный SMTP стоит подключить сразу. Во встроенной почте
облака жёсткие лимиты, а на self-hosted её нет вовсе — иначе подтверждение
адреса и приглашения придётся переделывать при переезде.

---

## 7. Пока проект в облаке

Настоящие персональные данные — чужие паспорта, СНИЛС, адреса — в облачный
проект заносить не стоит: требование локализации закрывается только переездом
на российский хостинг. Демонстрационный набор в `supabase/seed.sql` полностью
выдуман и для разработки достаточен.
