# Модель данных

Таблицы, связи между ними, правила доступа и инварианты, которые держит база.
Документ отвечает на вопрос «почему так, а не иначе» — перечень колонок всегда
можно посмотреть в миграциях.

---

## 1. Главное решение: арендатор — пространство, а не человек

Всё содержимое продукта принадлежит рабочему пространству, а не пользователю.
Дело, документ, объект, тип объекта — у каждого есть `workspace_id`.

Почему так. Юрист начинает один, через полгода нанимает помощника. Если бы
дела принадлежали человеку, передача означала бы миграцию данных с
переписыванием владельца у сотен строк. С пространством достаточно добавить
второго участника.

```
profiles ──< workspace_members >── workspaces
                                        │
                    ┌───────────────────┼────────────────────┐
                    │                   │                    │
                  cases            entity_types         workspace_invites
                    │
        ┌───────────┼───────────┬──────────────┐
        │           │           │              │
    entities   documents   chat_messages    activity
                    │
        ┌───────────┴────────────┐
        │                        │
 document_reviews         document_chunks
        │
  review_findings ──< finding_practice >── court_practice
```

## 2. Люди и доступ

| Таблица | Назначение |
|---|---|
| `profiles` | Публичные данные пользователя. `auth.users` наружу не отдаётся |
| `workspaces` | Арендатор: имя, слаг, реквизиты организации, тариф |
| `workspace_members` | Роль в пространстве: `owner`, `admin`, `member`, `viewer` |
| `workspace_invites` | Приглашения по почте с секретным токеном и сроком |

**Роли устроены по убыванию прав.** `viewer` смотрит, `member` пишет, `admin`
приглашает и меняет реквизиты, `owner` может удалить пространство. Отдельно
существует `platform_role` в профиле — уровень всей установки, `user` или
`admin`; администратор видит сводную статистику по всем пространствам.

**Инварианты, которые держит база, а не приложение:**

- *Владелец есть всегда.* Триггер `protect_last_owner` не даёт снять роль с
  последнего владельца или удалить его — иначе пространство осталось бы без
  того, кто им распоряжается.
- *Себя нельзя повысить до администратора установки.* Политика разрешает
  править свою строку профиля, но триггер `protect_platform_role` запрещает
  менять эту колонку кому-либо, кроме действующего администратора.
- *Текущее пространство — только своё.* Триггер `protect_last_workspace` не
  даёт записать в `last_workspace_id` пространство, в котором вы не состоите.

**Регистрация обрабатывается триггером** `handle_new_user`: заводится профиль,
личное пространство, членство с ролью владельца, и принимаются приглашения,
отправленные на этот адрес до регистрации. Должность и название организации
приходят в метаданных формы.

Уже зарегистрированному человеку приглашение выдаёт функция
`accept_pending_invites()` при входе: сам себе членство он вписать не может —
политика требует роли владельца в том пространстве, куда его зовут.

## 3. Продукт

| Таблица | Назначение |
|---|---|
| `entity_types` | Типы объектов. `workspace_id IS NULL` — встроенный, общий для всех |
| `cases` | Дела |
| `entities` | Объекты дела; реквизиты в `jsonb` |
| `documents` | Файлы: бакет и путь, **не URL** |
| `chat_messages` | Переписка с ассистентом вместе с находками и ссылками |
| `activity` | Лента действий по делу |

**Реквизиты лежат в `jsonb`, а не в колонках.** Продукт обещает, что человек
заведёт свой тип объекта — «транспортное средство», «студенческая работа» —
и он будет работать наравне со встроенными. Колонки под это не подходят:
каждый новый тип требовал бы миграции.

**Описание реквизитов хранится в `entity_types.fields`** массивом объектов:
ключ, подпись, обязательность, шаблон формата. Форма повторяет
`EntityFieldSchema` во фронте, поэтому перевод сводится к смене стиля имён.

**Путь к файлу, а не адрес.** В `documents` лежат `bucket` и `path`; ссылка
собирается на клиенте. Полный URL привязан к адресу проекта и сломался бы при
переезде на self-hosted.

### Инварианты

- *Валидность считает база.* Триггер `entities_validate` вызывает
  `app.validate_entity` при каждой записи и переписывает `validation_errors`.
  Клиент может прислать что угодно — объявить объект валидным он не может.
  Это ровно то, ради чего продукт существует.
- *Правка типа пересчитывает его объекты.* Добавили обязательное поле — все
  объекты этого типа немедленно становятся невалидными (`revalidate_type_entities`).
- *Принадлежность пространству не принимается от клиента.* У объектов,
  документов и сообщений `workspace_id` проставляется триггером из дела.
  Иначе запись можно было бы приписать к чужому пространству.
- *Тип должен быть доступен в пространстве.* Попытка создать объект типа из
  чужого пространства падает с исключением.

## 4. Работа с моделью

| Таблица | Назначение |
|---|---|
| `ai_jobs` | Очередь и журнал: вход, выход, модель, токены, стоимость, правка |
| `document_reviews`, `review_findings` | Разбор договора по пунктам |
| `court_practice`, `finding_practice` | Судебная практика |
| `document_chunks` | Фрагменты документов с векторами и полнотекстом |

`ai_jobs` — одновременно очередь и журнал. Это не экономия на таблицах: журнал
всё равно нужен для учёта расхода, а очередь без журнала теряет историю
попыток. Подробности — в [AI-BACKEND.md](./AI-BACKEND.md).

**`source` в `court_practice`** разводит демонстрационные акты и будущего
лицензированного поставщика. Поле `holding` допускает `NULL`: часть лицензий
запрещает хранить тексты у себя, тогда в базе остаются только реквизиты акта
и ссылка.

**Размерность вектора — 1024**, привязана к модели эмбеддингов. Смена модели
потребует миграции и переиндексации, поэтому рядом хранится `embedding_model`:
видно, чем считали.

## 5. Правила доступа

Правило одно и повторяется во всех политиках: **строку видно, если ты участник
её пространства; менять можешь, если роль не `viewer`.** Администратор
установки видит всё — это нужно админ-панели.

Вспомогательные функции живут в схеме `app`, которая не публикуется через
REST:

| Функция | Что проверяет |
|---|---|
| `app.current_user_id()` | Кто спрашивает. Единственное место, знающее формат токена |
| `app.is_member(ws)` | Состоит ли в пространстве |
| `app.has_workspace_role(ws, roles)` | Есть ли одна из ролей |
| `app.can_write(ws)` | Роль не `viewer` |
| `app.is_platform_admin()` | Администратор установки |

**`SECURITY DEFINER` у проверок обязателен, а не удобен.** Политика на
`workspace_members` не может сама читать `workspace_members` — Postgres уйдёт
в бесконечную рекурсию. Функция выполняется с правами владельца и читает
таблицу в обход политик.

**Смена механизма аутентификации правит одну функцию.** Про формат токена
знает только `app.current_user_id()`; переезд на другой Postgres не потребует
трогать сотню политик.

## 6. Хранилище

| Бакет | Доступ |
|---|---|
| `case-documents` | Закрытый. Путь `<workspace_id>/<case_id>/<uuid>-<имя>`, а у файла без дела — `<workspace_id>/loose/<uuid>-<имя>` |
| `avatars` | Публичный на чтение, запись только в свою папку |

Право на файл выводится из первого сегмента пути: `app.storage_workspace()`
достаёт из него идентификатор пространства, а политика сверяет членство.
Отдельной таблицы разрешений нет — и не нужно.

**Путь считает сервер, а не браузер.** Клиент получает готовый путь от
`prepareDocumentUploadAction`, загружает файл и просит зарегистрировать
строку; действие ещё раз сверяет, что путь относится к тому самому делу.

**Бакеты заводятся миграцией**, а не кнопкой в панели: иначе на новом сервере
их просто не будет.

## 7. Статистика

| Что | Кому |
|---|---|
| `workspace_stats` | Участникам — показатели своего пространства |
| `ai_usage_daily` | Участникам — расход по дням, задачам и моделям |
| `platform_overview()` | Только администратору установки |
| `platform_workspaces()` | Только администратору: пространства с владельцами |
| `platform_signups(days)` | Только администратору: регистрации по дням |

Представления объявлены с `security_invoker = true` — политики применяются к
тому, кто спрашивает. Без этого флага представление обходит RLS и показало бы
чужие данные.

Функции админ-панели проверяют права внутри и падают с исключением, если
спрашивает не администратор; право на исполнение отозвано у анонимного.

## 8. Переезд на self-hosted

Заложено с самого начала и отдельной подготовки не потребует:

1. **Схема в миграциях** — воспроизводится одной командой на любом Postgres.
2. **В базе пути к файлам, не URL** — смена адреса проекта ничего не ломает.
3. **Адреса и ключи в переменных окружения** — в коде их нет.
4. **`app.current_user_id()`** — единственное место, знающее про формат токена.
5. **Бакеты заводятся миграцией**, а не кнопкой в панели.

Отдельно: собственный SMTP стоит подключить сразу. Во встроенной почте облака
жёсткие лимиты, а на self-hosted её нет вовсе.
