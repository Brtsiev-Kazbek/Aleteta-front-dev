## 1. Что вообще происходит

Сейчас ваш фронт хранит данные в памяти браузера (Zustand). Обновил страницу —
всё исчезло. Бэкенд решает три задачи:

1. **Хранить** дела, сущности, документы — чтобы не пропадали.
2. **Считать** то, что нельзя доверить браузеру: генерация файлов, вызовы ИИ,
   ключи от платных API.
3. **Отдавать** данные фронту по HTTP.

### Словарь

| Слово | Что значит |
|---|---|
| **API** | Набор адресов, по которым фронт спрашивает данные |
| **Эндпоинт** | Один такой адрес, например `GET /v1/cases` |
| **FastAPI** | Библиотека Python, чтобы писать эндпоинты |
| **Uvicorn** | Программа, которая запускает ваше приложение |
| **Postgres** | База данных — где реально лежат дела и сущности |
| **ORM (SQLAlchemy)** | Позволяет работать с базой через объекты Python, а не писать SQL руками |
| **Миграция (Alembic)** | Скрипт, который меняет структуру таблиц. Нужен, чтобы не ломать данные при изменениях |
| **Pydantic** | Проверяет, что пришедший JSON правильной формы |
| **Docker** | Запускает Postgres одной командой, не устанавливая его в систему |

## 2. Архитектура

### Почему НЕ микросервисы на старте

Микросервисы — это когда каждая часть системы живёт отдельной программой и они
общаются по сети. Звучит солидно, но для первого бэкенда это ловушка:

- вместо одной программы отлаживаете пять;
- ошибка «сервис не отвечает» вместо понятного стектрейса;
- любое изменение задевает два-три репозитория.

**Делаем один сервис.** Но раскладываем его так, чтобы позже отрезать куски без
переписывания. Секрет простой:

> Вся бизнес-логика живёт в папке `services/` и **не знает про FastAPI**.
> Эндпоинты в `routers/` — тонкая обёртка, которая просто зовёт функции из
> `services/`.

Когда придёт время выделить, например, генерацию документов в отдельный сервис —
вы берёте `services/docgen.py`, оборачиваете своим FastAPI и меняете один вызов
функции на один HTTP-запрос. Логику трогать не нужно.

### Из чего состоит

```
┌─────────────┐     HTTP      ┌──────────────────────────┐
│   Фронт     │ ────────────▶ │   FastAPI приложение     │
│  (Next.js)  │ ◀──────────── │                          │
└─────────────┘               │  routers/  — эндпоинты   │
                              │  services/ — логика      │
                              │  models/   — таблицы     │
                              └───────┬──────────┬───────┘
                                      │          │
                              ┌───────▼──┐   ┌───▼────────┐
                              │ Postgres │   │ Диск/файлы │
                              │ + вектора│   │  uploads/  │
                              └──────────┘   └────────────┘
                                      │
                              ┌───────▼──────┐
                              │ Anthropic API│
                              └──────────────┘
```

Всего **две** внешние вещи: база данных и API модели. Файлы на первом этапе
кладём в обычную папку на диске — потом заменим на S3, это один файл кода.

## Целевой стек и порядок внедрения

Полный production-стек и **этап, на котором каждый инструмент реально нужен**.
Ничего не выброшено — вопрос только в очерёдности. Ставить всё сразу нельзя:
вы потратите месяц на инфраструктуру и не дойдёте до продукта.

### Этап 1 — продукт без ИИ (шаги 1–7)

| Инструмент | Зачем |
|---|---|
| Python 3.12+, FastAPI, Uvicorn | Само приложение |
| Pydantic v2 | Проверка входящих и исходящих данных |
| SQLAlchemy 2.0 (async), Alembic | Работа с базой и миграции |
| PostgreSQL 16 (образ `pgvector`) | Хранение всего |
| Docker Compose | Одна команда поднимает базу |
| pytest, httpx | Тесты |
| docxtpl | Генерация пакета документов |
| **Фронт:** TanStack Query, openapi-typescript | Запросы, кэш, типы из OpenAPI |

Файлы — в папку на диске за обёрткой `storage.py`. Фоновые задачи —
`BackgroundTasks`. Redis не нужен.

### Этап 2 — ИИ на связи (шаги 8–9)

| Инструмент | Зачем |
|---|---|
| OpenRouter **или** прямой Anthropic SDK | Вызовы модели (см. заметку ниже) |
| Кэш в таблице `llm_cache` | Не платить дважды |
| Таблица `llm_usage` | Видеть, куда уходят деньги |

### Этап 3 — документы и RAG (шаги 10–13)

| Инструмент | Зачем |
|---|---|
| pgvector | Хранение и поиск векторов |
| PyMuPDF | Быстрое извлечение текста из цифровых PDF |
| Tesseract OCR | Сканы и фотографии |
| Эмбеддинги через API | Старт без своего GPU |
| Redis + ARQ | Очередь: парсинг и эмбеддинги вне HTTP-запроса |
| MinIO | Файлы переезжают с диска в объектное хранилище |

Здесь `BackgroundTasks` перестаёт справляться: парсинг 80-страничного PDF с OCR
занимает минуты, и при перезапуске приложения задача теряется. ARQ переживает
рестарт и умеет ретраи.

### Этап 4 — выход в продакшен

| Инструмент | Зачем |
|---|---|
| PyJWT + HTTPOnly cookies | Авторизация |
| Traefik | Reverse-proxy и автоматический SSL |
| GitHub Actions | Линт, тесты, деплой |
| Ubuntu Server LTS | Хостинг |
| Sentry | Ошибки фронта и бэка в реальном времени |
| **Бэкапы Postgres** | См. «чего не хватает» |
| **Rate limiting** | См. «чего не хватает» |

Sentry ставьте **до** Prometheus. Он отвечает на вопрос «что сломалось у
пользователя», а это на старте важнее графиков нагрузки.

### Этап 5 — масштаб и наблюдаемость

| Инструмент | Когда |
|---|---|
| Prometheus + Grafana | Когда есть нагрузка, за которой надо следить |
| Loki + Promtail | Когда контейнеров больше двух и логи теряются |
| BGE-M3 своим хостингом | Когда объём эмбеддингов оправдает GPU-сервер |
| bge-reranker-v2-m3 | Когда качество поиска упрётся в потолок |
| Docling / Unstructured | Когда PyMuPDF не справится со сложными таблицами |
| LlamaIndex | Только если ручной RAG станет тесен |
| Микросервисы | По швам из `services/` |

### Заметки по конкретным решениям

**OpenRouter и кэширование промптов.** Единый шлюз удобен: одна интеграция,
переключение моделей строкой в конфиге. Но вы просили экономить токены, а
главный рычаг в чате — prompt caching (кэш системного промпта и контекста дела
на стороне провайдера). Через посредника его поведение зависит от того, как
шлюз пробрасывает параметры кэширования, и это надо проверять. Практичный
компромисс: интерфейс `AIClient` из шага 8 остаётся, а под ним две реализации —
прямой Anthropic там, где важен кэш (чат, анализ рисков), и OpenRouter для
всего остального. Переключение — одна строка, потому что вызывающий код о
провайдере не знает.

**LlamaIndex.** Мощный, но это ещё один слой абстракции поверх того, что у вас
и так есть. Ваш RAG — это «порезать, получить эмбеддинги, положить в pgvector,
искать гибридно». Прямым кодом это ~200 строк, которые вы полностью понимаете
и можете отладить построчно. С LlamaIndex вы получите те же 200 строк плюс
необходимость разбираться, почему фреймворк внутри делает не то. Берите его,
когда понадобятся его продвинутые вещи — маршрутизация по нескольким индексам,
графовые запросы. Не раньше.

**BGE-M3 и reranker — это свой сервер.** Обе модели вы хостите сами. На CPU
BGE-M3 работает, но медленно; reranker на CPU для top-30 — это заметные секунды
на запрос. Полноценно нужен GPU, то есть отдельная машина и её обслуживание.
Начните с эмбеддингов через API: дороже за штуку, но ноль инфраструктуры.
Переезжайте на свой хостинг, когда посчитаете, что GPU-сервер дешевле счетов
за API — это честная точка перехода, а не вопрос вкуса.

**Zod не надо зеркалить руками.** FastAPI сам отдаёт OpenAPI-схему. Прогоняете
её через `openapi-typescript` — и типы фронта **генерируются** из бэкенда.
Ручное зеркалирование Pydantic ↔ Zod разъедется через месяц, и вы узнаете об
этом от пользователя. Zod оставьте для того, что бэкенд не покрывает: формы
до отправки, парсинг данных из URL.

**TanStack Query и ваш нынешний Zustand.** Сейчас `useAppStore` держит и
серверные данные (`cases`, `entities`, `documents`), и состояние интерфейса
(`isSidebarExpanded`, `selectedCaseIds`, `editingCell`, `isCustomSchemaOpen`).
Когда появится API, серверная часть должна уехать в TanStack Query — он сам
умеет кэш, инвалидацию и поллинг статуса задач генерации. В Zustand останется
только интерфейсное состояние. Это не косметика: сейчас после `PATCH` вам
пришлось бы руками синхронизировать локальный массив с ответом сервера, а
TanStack Query делает это инвалидацией ключа.

**Cookies требуют защиты от CSRF.** HTTPOnly-cookie правильно защищает токен от
чтения скриптом, но браузер прикладывает её к запросам автоматически — в том
числе к запросам с чужого сайта. Нужны `SameSite=Lax` минимум и CSRF-токен на
изменяющих запросах. С заголовком `Authorization` этой проблемы нет, но там
уязвим сам токен. Выбирайте осознанно.

### Чего в списке не хватает

Это не придирки — для продукта с юридическими документами каждый пункт
обязателен.

**Бэкапы Postgres.** В списке есть Prometheus и Grafana, но нет бэкапов. У вас
хранятся дела клиентов; потеря базы — это конец продукта, а не инцидент.
Минимум: `pg_dump` по расписанию в отдельное хранилище + **проверенное
восстановление**. Бэкап, который ни разу не разворачивали, бэкапом не является.

**Проверка загружаемых файлов.** Пользователи заливают произвольные PDF и DOCX.
Нужны: ограничение размера, проверка реального типа файла (по содержимому, а не
по расширению) и антивирус (ClamAV) перед парсингом.

**Rate limiting.** За вашими эндпоинтами стоят платные вызовы модели. Без
ограничения частоты один скрипт может выставить вам счёт. Уровень Traefik или
`slowapi` в приложении.

**Метрика стоимости в Prometheus.** Раз уж он будет — выводите туда не только
CPU и память, но и токены с рублями по `task_type`. Это единственный способ
заметить, что после правки промпта расход вырос втрое.

## Шаг 1. Пустое приложение

**Зачем.** Убедиться, что Python и FastAPI работают, до всякой сложности.

**Что делать.**

```bash
mkdir aleteya-backend
cd aleteya-backend
uv init
uv add fastapi uvicorn
```

Создайте `app/main.py`:

```python
from fastapi import FastAPI

app = FastAPI(title="Алетейя API")

@app.get("/health")
def health():
    return {"status": "ok"}
```

Запустите:

```bash
uv run uvicorn app.main:app --reload
```

**Проверка.** Откройте http://localhost:8000/docs — увидите автоматическую
документацию с эндпоинтом `/health`. Нажмите «Try it out» → «Execute», получите
`{"status": "ok"}`.

> `--reload` означает: меняете код — сервер сам перезапускается. Для разработки
> всегда так.

## Шаг 2. База данных

**Зачем.** Данные должны переживать перезапуск.

**Что делать.**

Создайте `docker-compose.yml`:

```yaml
services:
  db:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_USER: aleteya
      POSTGRES_PASSWORD: aleteya
      POSTGRES_DB: aleteya
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

Образ `pgvector` — это обычный Postgres плюс умение хранить вектора. Понадобится
на шаге 10, ставим сразу, чтобы не переделывать.

Запустите:

```bash
docker compose up -d
```

Поставьте библиотеки:

```bash
uv add sqlalchemy psycopg[binary] alembic pydantic-settings
```

`.env`:

```
DATABASE_URL=postgresql+psycopg://aleteya:aleteya@localhost:5432/aleteya
ANTHROPIC_API_KEY=пока_пусто
```

`app/config.py` — читает `.env`, отдаёт настройки.
`app/db.py` — создаёт подключение и функцию `get_db()`, которую FastAPI будет
подсовывать в эндпоинты.

Настройте Alembic:

```bash
uv run alembic init migrations
```

**Проверка.** `docker compose ps` показывает контейнер `Up`. Приложение
стартует без ошибок подключения.

## Шаг 3. Первые эндпоинты — дела

**Зачем.** Самая простая сущность. На ней осваиваете весь цикл: таблица →
миграция → модель → эндпоинт.

**Что делать.**

1. **Таблица** — `app/models/case.py`. Поля повторяют ваш фронтовый тип `Case`:
   `id`, `title`, `status`, `tags`, `description`, `context_file`, `created_at`.

2. **Миграция** — создать и применить:

```bash
uv run alembic revision --autogenerate -m "cases"
uv run alembic upgrade head
```

Первая команда сравнивает модели с базой и пишет скрипт изменений. Вторая —
применяет его. **Каждый раз, когда меняете модель, повторяйте обе.**

3. **Схемы** — `app/schemas/case.py`: `CaseCreate` (что принимаем),
   `CaseRead` (что отдаём). Это разные вещи: при создании нет `id` и `created_at`.

> ### ⚠️ Решение, которое нельзя отложить: регистр полей
>
> Python пишет `cadastral_number`, JavaScript — `cadastralNumber`. Если бэкенд
> будет отдавать snake_case, при подключении фронта вам придётся переименовывать
> каждое поле и ловить `undefined`.
>
> Настраивается один раз в базовом классе схем:
>
> ```python
> from pydantic import BaseModel, ConfigDict
> from pydantic.alias_generators import to_camel
>
> class ApiModel(BaseModel):
>     model_config = ConfigDict(
>         alias_generator=to_camel,   # наружу camelCase
>         populate_by_name=True,      # внутрь принимаем оба варианта
>         from_attributes=True,       # можно отдавать объекты SQLAlchemy
>     )
> ```
>
> Все схемы наследуете от `ApiModel`. Внутри Python код остаётся привычным
> snake_case, а API говорит на языке фронта. **Сделайте это на первой же схеме** —
> потом переделывать больно.
>
> Ключи внутри `data` у сущностей (`cadastralNumber`, `field_1`) это не
> затрагивает — они хранятся в JSONB как есть.

4. **Эндпоинты** — `app/routers/cases.py`:

```

GET    /v1/cases          список
GET    /v1/cases/{id}     одно дело
PATCH  /v1/cases/{id}     изменить
DELETE /v1/cases/{id}     удалить
```

5. Подключить роутер в `main.py`: `app.include_router(cases.router)`.

**Проверка.** В `/docs` создайте дело, потом получите список — оно там.
Перезапустите сервер — дело на месте. Это и есть разница с Zustand.

**Зачем.** Сердце продукта — красная подсветка незаполненных полей. Логика уже

## Шаг 10. RAG — поиск по документам

**Зачем.** Нельзя отправить модели договор на 80 страниц: дорого и она
«потеряет» середину. Нужно находить и отправлять только нужные куски.

### Как это работает простыми словами

1. Документ режем на кусочки («чанки») по 2–3 абзаца.
2. Каждый кусочек прогоняем через модель эмбеддингов — она превращает текст в
   список чисел (вектор). Похожие по смыслу тексты дают близкие вектора.
3. Вектора складываем в Postgres (для этого и брали `pgvector`).
4. Когда пользователь спрашивает — превращаем вопрос в вектор и ищем самые
   близкие кусочки.
5. Отправляем модели **только их**, а не весь документ.

### Что делать

```bash
uv add pymupdf python-docx
```

1. **`app/services/ingest.py`** — конвейер обработки файла:
   - PDF → текст (`pymupdf`), DOCX → текст (`python-docx`);
   - убрать колонтитулы и номера страниц;
   - **резать по структуре**, а не вслепую: по нумерации пунктов
     (`1.1`, `2.3`, «Статья», «Пункт»). Если структуры нет — окнами по ~600
     слов с перехлёстом. Метку пункта сохраняем — она понадобится на шаге 13,
     чтобы подсвечивать абзац;
   - получить эмбеддинги **пачкой** (все чанки одним запросом, не по одному);
   - сохранить в базу.

2. **Таблица `doc_chunks`**: `id`, `document_id`, `case_id`, `text`, `page`,
   `clause`, `embedding` (vector), `tsvector`.

3. **`app/services/rag.py`** — поиск. **Обязательно гибридный:**
   - векторный поиск (по смыслу) — top-30;
   - полнотекстовый поиск Postgres (по словам) — top-30;
   - объединяем, берём лучшие 8.

> Зачем два поиска. «Кадастровый номер 15:09:0000000:0000» — точная строка,
> её находит текстовый поиск, а векторный запросто промахнётся. «Риски по
> срокам оплаты» — наоборот, тут нужен смысл. По отдельности каждый метод
> проваливает половину запросов.

4. **Всегда фильтруйте по `case_id`.** Иначе в ответе по одному делу всплывут
   документы другого клиента.

5. Ingest запускать при загрузке файла (шаг 6), статус документа менять
   `processing` → `ready`.

**Проверка.** Загрузили выписку ЕГРН, дождались `ready`, дёрнули
`POST /v1/cases/{id}/search` с запросом «площадь участка» — вернулись куски

## Тестирование

Тесты пишем не «для галочки», а чтобы менять код без страха.

```bash

```

### Как проверять, не поднимая всё

**1. Логика без базы и сети.** `services/validation.py`, чанкинг, сборка
промптов — обычные функции. Тест выглядит так:

```python
def test_empty_required_field_gives_error():
    result = validate_entity({"name": "Участок"}, LAND_SCHEMA)
    assert "landUse" in result.field_errors
```

Секунды на весь набор. Сюда должно попадать большинство тестов.

**2. Эндпоинты без запущенного сервера.** FastAPI умеет вызывать себя изнутри:

```python
from fastapi.testclient import TestClient

def test_create_case():
    client = TestClient(app)
    response = client.post("/v1/cases", json={"title": "Тест"})
    assert response.status_code == 201
```

Никакого `uvicorn`, никакой сети.

**3. ИИ без денег.** Тот самый `FakeClient` из шага 8. Ставите
`AI_PROVIDER=fake` — все фичи с моделью тестируются бесплатно и мгновенно.
Заготовки ответов кладите в `tests/fixtures/`.

**4. База.** Либо отдельная тестовая база в докере, либо `pytest` фикстура,
которая создаёт таблицы перед тестом и удаляет после.

### Проверка руками

`/docs` — ваш главный инструмент. Каждый эндпоинт можно дёрнуть прямо оттуда,
не открывая фронт и не устанавливая Postman.

## Когда что-то сломалось

| Симптом | Обычная причина |
|---|---|
| `connection refused` к базе | Не запущен `docker compose up -d` |
| `relation "cases" does not exist` | Забыли `alembic upgrade head` |
| Изменили модель — ничего не поменялось | Нужны обе команды: `revision --autogenerate`, потом `upgrade head` |
| Фронт: ошибка CORS | Не добавлен `CORSMiddleware` или неверный порт в `allow_origins` |
| `401` от Anthropic | Ключ не подхватился из `.env` |
| Запрос висит и обрывается | Долгая операция выполняется синхронно — выносите в задачу (шаг 7) |
| Модель отвечает выдумками | В промпт не попал контекст, либо RAG ничего не нашёл |

**Как читать ошибку.** Питон печатает «стектрейс» — список вызовов. Читайте
**снизу вверх**: последняя строка говорит, что случилось, а строки выше —
где именно. Ищите первую строку, где упомянут *ваш* файл.

## Куда расти дальше

Полная раскладка инструментов по этапам — в разделе
[Целевой стек](#целевой-стек-и-порядок-внедрения). Здесь коротко о том, что
идёт после базовых 14 шагов:

1. **Авторизация.** Пока эндпоинты открыты. PyJWT + HTTPOnly cookies и
   `tenant_id` в каждой таблице, чтобы клиенты не видели дела друг друга.
   Не забудьте про CSRF — см. заметку в разделе про стек.
2. **MinIO вместо диска.** Меняется только `storage.py`.
3. **ARQ вместо `BackgroundTasks`.** Обязательно к моменту, когда появится OCR:
   такие задачи не должны теряться при перезапуске приложения.
4. **Sentry.** Раньше Prometheus: «что сломалось у пользователя» важнее
   графиков нагрузки.
5. **Бэкапы и rate limiting.** До первого реального клиента, не после.
6. **Evals для ИИ.** Наберите 20 документов с заранее известными ответами и
   гоняйте ночью: считайте точность **и стоимость в токенах на документ**. Без
   этого «модель стала хуже» вы заметите только по жалобам.
7. **Вот теперь микросервисы.** Если какая-то часть станет узким местом —
   берёте её папку из `services/`, оборачиваете FastAPI, меняете вызов функции
   на HTTP. Логика не переписывается, потому что вы с самого начала не смешали
   её с фреймворком.

## С чего начать завтра

Шаги 1–5. Это даёт полностью рабочий продукт: дела, сущности, валидация,
